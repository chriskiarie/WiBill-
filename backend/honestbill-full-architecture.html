// System Design Document — HonestBill

Hotspot
Billing
Platform

A multi-tenant SaaS platform that lets independent ISPs deploy branded captive portals, accept M-Pesa payments, and manage MikroTik hotspot access — automatically. You run the infrastructure. ISPs plug in. Users pay. Everyone gets what they paid for.

The core insight no existing ISP billing system has: network availability must be a first-class citizen in every billing decision. A user connects to WiFi → your system checks if that WiFi is actually up → if it is, they can pay and get access → if it's not, they're told exactly what's happening before they hand over a single shilling. This is not a feature. It is the product.

02 The Core Transaction Flow
Happy path — user pays, gets internet
01
Connect to WiFi
User's device joins hotspot SSID. MikroTik intercepts all HTTP traffic. Redirects browser to:
https://pay.honestbill.co.ke/portal/{isp_slug}?mac=XX:XX:XX&ip=192.168.x.x
MIKROTIK
02
Network Status Check
Portal loads. System immediately pings the ISP's uplink. If UP → show packages normally. If DOWN → show honest status: "Service is currently down. Estimated restoration: checking..." No pay button shown.
YOUR BACKEND
03
Package Selection
User sees ISP-branded portal with packages (defined by ISP admin). Selects plan. Enters M-Pesa phone number. Hits PAY.
USER
04
STK Push Initiated
Backend calls Daraja API → STK Push to user's phone. M-Pesa prompt appears on user's screen. Portal shows "Waiting for M-Pesa confirmation..." with polling.
DARAJA API
05
M-Pesa Confirms Payment
User enters PIN. Safaricom calls your callback URL:
POST /api/mpesa/callback/{tenant_id}
ResultCode=0 → payment confirmed. Receipt extracted.
SAFARICOM
06
MikroTik Session Created
Backend calls RouterOS API → creates hotspot user with MAC address binding + session duration. User's device is now authorized. Internet opens automatically.
YOUR BACKEND
07
Revenue Split Recorded
Transaction recorded: amount_ksh, platform_fee_ksh (your cut), isp_earnings_ksh. ISP balance updated. You settle with ISPs weekly.
YOUR BACKEND
08
Session Expires → Auto-Kick
APScheduler checks expiring sessions every minute. On expiry: RouterOS API removes hotspot user. User is redirected back to captive portal. They can buy again.

05 M-Pesa Daraja Integration
01 — STK Push Request
# POST /api/portal/{slug}/pay # User selects package, enters phone payload = { "BusinessShortCode": tenant.shortcode, "Password": generate_password(), "Timestamp": now_str, "TransactionType": "CustomerPayBillOnline", "Amount": package.price_ksh, "PartyA": phone_number, "PartyB": tenant.shortcode, "PhoneNumber": phone_number, "CallBackURL": callback_url, "AccountReference": session_id, "TransactionDesc": package.name } # Store CheckoutRequestID for matching # Return 202 to portal — polling begins
02 — Callback Handler
# POST /api/mpesa/callback/{tenant_id} # Safaricom calls this after user pays if result_code == 0: # Extract receipt, amount, phone receipt = extract_receipt(payload) # Record transaction (idempotent) await record_transaction( session_id, receipt, amount ) # Authorize MikroTik immediately await mikrotik.add_hotspot_user( mac=session.mac_address, profile=package.name, duration=package.duration_hours ) # Update session → active session.status = "active" session.started_at = now() session.expires_at = now() + duration else: # Payment failed → notify portal session.status = "failed"
03 — Portal Polling
# Portal polls every 3 seconds # GET /api/session/{session_id}/status while elapsed < 90: status = await poll_session() if status == "active": # Redirect to success page # Show timer countdown break if status == "failed": # Show failure message # Offer retry — no double charge break # Still pending — show spinner await sleep(3) # Timeout after 90s → STK expired # Prompt user to try again
04 — Security Rules
# Callback endpoint hardened: # 1. Whitelist Safaricom IPs only ALLOWED_IPS = [ "196.201.214.200", "196.201.214.206", "196.201.213.114", # ...all Daraja IPs ] # 2. Verify receipt uniqueness # mpesa_receipt is UNIQUE in DB # Duplicate callback = no-op # 3. STK push rate limit # 1 per phone per 30 seconds # Stored in Redis # 4. Amount validation # Confirm paid amount matches # package price exactly

08 Security Architecture
🔐Secrets
Encryption at Rest
  • All MikroTik passwords encrypted with Fernet before DB insert
  • All M-Pesa credentials (consumer key, secret, passkey) encrypted
  • Master encryption key in environment only — never in DB
  • Separate keys per environment (dev vs prod)
🌐Network
Transport Security
  • HTTPS everywhere — Cloudflare handles TLS termination free
  • Daraja callback endpoint: Safaricom IP whitelist only
  • MikroTik API: your server IP whitelisted on router firewall
  • Redis not exposed externally — internal Railway network only
⏱Rate Limiting
Abuse Prevention
  • STK Push: 1 per phone number per 30 seconds (Redis)
  • Portal: 10 requests per IP per minute
  • Payment endpoint: 3 attempts per MAC per hour
  • Admin API: separate rate limits, stricter
✓Idempotency
No Double Charges
  • mpesa_receipt is UNIQUE constraint in DB
  • Duplicate callback = silent no-op, no second session created
  • CheckoutRequestID tracked: can't initiate two for same session
  • Amount validated against package price on callback
👤Access Control
Auth & Roles
  • Platform admin and ISP admin are separate JWT contexts
  • ISP admin can only see their own tenant data
  • Platform admin sees all tenants
  • Portal has no auth — anonymous by design (MAC-based identity)
📋Audit
Full Audit Trail
  • Raw Daraja callbacks logged to mpesa_callbacks (append-only)
  • Every session state change timestamped
  • MikroTik API calls logged with result
  • Network events recorded — full uptime history per tenant
